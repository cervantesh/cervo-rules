# CervoRules v2 Public API Change Management

Issue: https://github.com/cervantesh/cervo-rules/issues/60

Date: 2026-05-21

Owner: CervoSoft / Codex

Status: Draft for maintainer review

## Executive Summary

CervoRules v2 is a proposed breaking public API redesign. The purpose is not to
rename things for aesthetics. The purpose is to remove structural limits in the
current v1 API before more consumers depend on them.

The v2 change should make CervoRules better at:

- returning complete operational decisions;
- supporting predicates and actions that can fail explicitly;
- separating decision output, trace, observations, and diagnostics;
- validating limits with complete violation sets;
- testing generated policies outside `testing.TB`;
- making generated policies easier to consume as runtime factories;
- preserving cross-domain agnosticism as CervoProxy uses more of the library.

This document is the change-management plan for that work. It defines what
breaks, why it breaks, how to sequence the implementation, how to verify it, how
to communicate it, and which extra opportunities were found during API review.

## Why This Is v2

The proposed changes affect compile-time contracts:

- interfaces;
- exported function signatures;
- generated Go APIs;
- public struct shape;
- consumer testkit helpers;
- validation and error behavior.

These are not compatible minor changes. A consumer that imports CervoRules,
defines custom predicates/actions, calls generated policies, or validates limits
will need source changes. That makes this a v2 line.

## Change Principles

1. Break only where the new API is materially better.
2. Keep the runtime core dependency-light.
3. Preserve CervoRules as cross-domain infrastructure, not CervoProxy-specific
   infrastructure.
4. Use explicit result and error types rather than overloading `Decision`.
5. Keep adapters optional. HTTP remains an adapter, not the identity of the
   library.
6. Prefer migration helpers where they reduce consumer risk.
7. Require consumer-shaped tests before migration is considered complete.
8. Keep optional derived-fact support in a separate package unless an ADR
   proves that core integration is necessary and cross-domain.

## Proposed Breaking Changes

### 1. `Engine.Decide` Returns `DecisionResult`

Current:

```go
type Engine interface {
    Decide(ctx context.Context, req Request) (Decision, error)
}
```

Proposed:

```go
type Engine interface {
    Decide(ctx context.Context, req Request) (DecisionResult, error)
}

type DecisionResult struct {
    Decision    Decision
    Trace       DecisionTrace
    Observation DecisionObservation
    Diagnostics ValidationErrors
}
```

Rationale:

- `Decision` should describe the decision, not every operational artifact.
- Trace and observation are distinct data products.
- Future diagnostics can be returned without adding more fields to `Decision`.

Migration:

```go
result, err := engine.Decide(ctx, req)
if err != nil { return err }
decision := result.Decision
```

Risk:

- High. This touches every consumer and many tests.

Mitigation:

- Provide a temporary helper:

```go
func DecideDecision(engine Engine, ctx context.Context, req Request) (Decision, error)
```

Only if it does not hide v2 semantics.

### 2. `Predicate.Evaluate` Returns Error

Current:

```go
type Predicate interface {
    Evaluate(EvalContext) PredicateResult
}
```

Proposed:

```go
type Predicate interface {
    Evaluate(context.Context, EvalContext) (PredicateResult, error)
}
```

Rationale:

- Dynamic predicates may need to fail.
- Evaluation errors should be visible in traces and results.
- Context cancellation should be available to predicate implementations.

Migration:

```go
func (p myPredicate) Evaluate(ctx context.Context, eval cervorules.EvalContext) (cervorules.PredicateResult, error) {
    return cervorules.PredicateResult{Matched: true, Name: "myPredicate"}, nil
}
```

Risk:

- High for custom predicates.

Mitigation:

- Provide adapter helper:

```go
func PredicateFunc(name string, fn func(EvalContext) PredicateResult) Predicate
```

### 3. `Action.Apply` Receives Context And Evaluation Facts

Current:

```go
type Action interface {
    Apply(DecisionMutator) error
    Name() string
}
```

Proposed:

```go
type Action interface {
    Apply(context.Context, EvalContext, DecisionMutator) error
    Name() string
}
```

Rationale:

- Actions should be able to inspect immutable evaluation data.
- Context-aware actions can respect cancellation.
- Custom actions become easier to observe and test.

Risk:

- High for custom actions.

Mitigation:

- Built-in action constructors are updated internally.
- Provide adapter helper:

```go
func ActionFunc(name string, fn func(DecisionMutator) error) Action
```

### 4. `CheckLimits` Returns All Violations

Current:

```go
func CheckLimits(limits Limits, requested RequestedLimits) error
```

Proposed:

```go
type LimitViolations []LimitViolation

func (v LimitViolations) Error() string
func (v LimitViolations) Has(field string) bool

func CheckLimits(limits Limits, requested RequestedLimits) LimitViolations
```

Rationale:

- Consumers can return complete validation feedback.
- CervoProxy can map body failures to `413` while still reporting other
  forbidden request attributes when useful.

Migration:

```go
violations := cervorules.CheckLimits(limits, requested)
if len(violations) > 0 {
    return violations
}
```

HTTP adapters should map `body_bytes` violations to `413` and other limit
fields to `403`:

```go
violations := cervorules.CheckLimits(limits, requested)
if len(violations) > 0 {
    status := http.StatusForbidden
    if violations.Has("body_bytes") {
        status = http.StatusRequestEntityTooLarge
    }
    return status, violations
}
```

Risk:

- Medium. Callers checking `err != nil` must change.

### 5. Testkit Becomes Error-First

Current:

```go
func AssertGeneratedRuntimePolicy(t testing.TB, contract GeneratedRuntimePolicyContract)
```

Proposed:

```go
func CheckGeneratedRuntimePolicy(contract GeneratedRuntimePolicyContract) error
func MustAssertGeneratedRuntimePolicy(t testing.TB, contract GeneratedRuntimePolicyContract)
```

Compatibility:

```go
// Deprecated: use MustAssertGeneratedRuntimePolicy or CheckGeneratedRuntimePolicy.
func AssertGeneratedRuntimePolicy(t testing.TB, contract GeneratedRuntimePolicyContract)
```

Rationale:

- Contract checks can run in tests, CLI smoke checks, release verification, or
  consumer migration tools.
- `Must...` names make fatal behavior explicit.

Risk:

- Low to medium.

### 6. Generated Policies Become Factories

Current generated API:

```go
BuildPolicy(overrides ...cervorules.PolicyRuntimeConfig) (*cervorules.CompiledDecisionFlow, error)
DefaultRuntimeConfig() cervorules.PolicyRuntimeConfig
ValidateRuntimeConfig(cfg cervorules.PolicyRuntimeConfig) error
```

Proposed generated API:

```go
type PolicyFactory struct{}

func NewPolicyFactory() PolicyFactory
func (PolicyFactory) DefaultConfig() cervorules.PolicyRuntimeConfig
func (PolicyFactory) ValidateConfig(cfg cervorules.PolicyRuntimeConfig) error
func (PolicyFactory) Build(ctx context.Context, cfg cervorules.PolicyRuntimeConfig) (*cervorules.CompiledDecisionFlow, error)
```

Rationale:

- Groups generated policy behavior.
- Allows future metadata, version, vocabulary, and schema helpers without adding
  more package-level functions.
- Makes generated packages easier to test as objects.

Risk:

- High for generated policy consumers.

Mitigation:

- One migration cycle with generated wrappers:

```go
// Deprecated: use NewPolicyFactory().Build(ctx, cfg).
func BuildPolicy(overrides ...cervorules.PolicyRuntimeConfig) (*cervorules.CompiledDecisionFlow, error)
```

### 7. `PolicyRuntimeConfig` Moves Toward Options Or Immutable Builder

Current:

```go
type PolicyRuntimeConfig struct {
    TrustedUsers []string
    DefaultTimeout time.Duration
    ...
}
```

Potential v2 shape:

```go
type PolicyRuntimeConfig struct {
    // fields may remain, but construction is encouraged through options
}

type RuntimeOption func(*PolicyRuntimeConfig)

func NewPolicyRuntimeConfig(options ...RuntimeOption) PolicyRuntimeConfig
func WithDefaultProvider(provider Provider) RuntimeOption
func WithCapabilityRoute(capability Capability, service Service) RuntimeOption
```

Rationale:

- Public fields are long-lived API.
- Options allow validation, normalization, and future extension.

Risk:

- Medium if fields stay public.
- High if fields become private.

Recommendation:

- For v2.0, add option constructors but keep fields public.
- Consider private fields only for v3 unless field misuse becomes severe.

### 8. `Vocabulary` Becomes Interface Plus Default Implementation

Current:

```go
type Vocabulary struct { ... }
```

Proposed:

```go
type Vocabulary interface {
    ValidateCapability(Capability) error
    ValidateService(Service) error
    ValidateProvider(Provider) error
    ValidateRequest(Request) error
    ValidateDecision(Decision) error
}

type StaticVocabulary struct { ... }
```

Rationale:

- Enables generated, remote, dynamic, or domain-specific vocabularies.
- Keeps validation behavior pluggable.

Risk:

- High because consumers construct `Vocabulary` today.

Mitigation:

- Rename current concrete implementation to `StaticVocabulary`.
- Keep `NewVocabulary` returning `Vocabulary`.

### 9. Structured Validation Errors

Current:

Most validation returns textual `error`.

Proposed:

```go
type ValidationError struct {
    Code   string
    Field  string
    Value  string
    Reason string
}

type ValidationErrors []ValidationError
```

Rationale:

- Consumers can render friendly errors.
- CI can inspect fields.
- Generated policy validation can expose stable diagnostics.
- `Code`, `Field`, `Value`, and `Reason` are stable fields for consumer
  branching and tests.

Risk:

- Medium. String matching tests must migrate.

### 10. `Decision` Decomposition

Current:

`Decision` includes allow/deny, route, provider, audit, retry, breaker, limits,
ruleset version, and trace.

Proposed:

```go
type Decision struct {
    Outcome DecisionOutcome
    Reason  string
    RuleID  string
    Route   DecisionRoute
    Runtime DecisionRuntime
    Audit   DecisionAudit
    Limits  Limits
}
```

Rationale:

- Reduces flat struct sprawl.
- Makes future additions easier.
- Separates route metadata from runtime behavior.

Risk:

- Very high because consumers access fields directly.

Recommendation:

- Defer until after `DecisionResult` unless a clear migration path is prepared.

### 11. Domain Primitive Rename Review

Candidates:

- `Provider` -> `Backend`, `Executor`, or `RuntimeProvider`
- `Service` -> `Target`, `Destination`, or `BackendService`
- `Capability` remains stable

Rationale:

- `Provider` is useful in gateway and AI routing but may be less neutral for
  billing, documents, or device orchestration.

Risk:

- Extremely high.

Recommendation:

- Do not include in v2.0 unless maintainers accept a broad migration.
- Open a separate ADR if this becomes necessary.

### 12. HTTP Adapter Generalization

Current:

HTTP helpers are direct public APIs.

Proposed:

```go
type FactsAdapter[T any] interface {
    FactsFrom(T) (RequestFacts, error)
}
```

Rationale:

- Supports queue messages, cron jobs, CLI commands, device telemetry, and HTTP
  without implying HTTP is the core runtime.

Risk:

- Low if additive.
- Medium if existing helper names change.

Recommendation:

- Add in v2 as additive API. Keep HTTP adapter optional.

## Additional Opportunities Found During API Review

### A. Explicit Versioned Module Path

If v2 ships as a Go major version, the module path should become:

```text
github.com/cervantesh/cervo-rules/v2
```

This is standard Go module behavior for v2+.

Impact:

- All imports change.
- Generated code must emit `/v2` imports.
- CervoProxy must update imports and regenerated policy packages.

Recommendation:

- Required for a true Go module v2 release.

Phase 1 foundation:

- Document v2 consumer imports as `github.com/cervantesh/cervo-rules/v2`.
- Document generated policy regeneration with v2 tools so generated code imports
  `/v2`.
- Keep v1 available through v1 release tags and package artifacts.
- Do not treat CervoProxy as migrated until its own migration PR updates imports,
  regenerated policy packages, tests, and build workflows.

### B. API Surface Report In CI

Add an API inventory artifact during release:

```bash
go doc ./... > api-doc.txt
```

or use a dedicated compatibility checker if accepted later.

Impact:

- Helps avoid accidental public API drift.

Classification:

- v2.x compatible improvement.

### C. Generated Policy Metadata

Generated policies should expose:

```go
func (PolicyFactory) Metadata() PolicyMetadata

type PolicyMetadata struct {
    Name          string
    DSLVersion    string
    GeneratedWith string
    VocabularyHash string
}
```

Impact:

- Helps CervoProxy and package consumers detect drift.

Classification:

- v2 candidate, additive within generated API.

### D. Stable Error Codes

Validation and limit errors should include stable codes:

```go
const ErrorCodeUnknownCapability = "unknown_capability"
const ErrorCodeLimitMaxTokens = "limit_max_tokens"
```

Impact:

- Better UX and API responses.

Classification:

- v2 candidate.

### E. Context Cancellation Semantics

Define whether context cancellation during evaluation returns:

- a top-level error;
- a denied decision;
- or a diagnostic result.

Recommendation:

- Return top-level error for cancellation.
- Do not silently deny on infrastructure cancellation.

Classification:

- v2 required if predicates/actions receive context.

### F. Policy Compilation Result

`Compile()` could return a richer result:

```go
type CompileResult struct {
    Engine *CompiledDecisionFlow
    Warnings ValidationErrors
}
```

Impact:

- Allows non-fatal policy warnings.

Classification:

- v2.x, not required for v2.0.

### G. Naming Consistency For Audit And Observability

`DecisionObservation` and `TraceSummary` should align with `DecisionResult`.

Potential improvement:

```go
func NewDecisionObservation(result DecisionResult) DecisionObservation
```

Classification:

- v2 candidate because it follows `DecisionResult`.

### H. Policygen Diagnostic Type Reuse

`internal/policygen.Diagnostics` could share public validation error concepts
or deliberately remain generator-private.

Recommendation:

- Keep generator diagnostics distinct but map to public error codes where useful.

Classification:

- v2.x.

### I. Migration Test Fixture For CervoProxy

Add a fixture or sample module that mimics CervoProxy integration:

- runtime config override;
- generated policy factory;
- HTTP adapter;
- limit checking;
- decision observation.

Classification:

- v2 implementation prerequisite.

### Phase 3: Predicate And Action Contracts

Goal:

Make evaluation context-aware and error-aware.

- adapter helpers for simple predicates/actions
- evaluation error propagation

DoD:

- Built-in predicates/actions are migrated.
- Custom predicate/action tests cover error propagation.

### Phase 4: Generated Policy Factory

Goal:

Replace package-level generated functions with a generated factory.

Changes:

- `PolicyFactory`
- `NewPolicyFactory`
- `PolicyFactory.Build`
- `PolicyFactory.DefaultConfig`
- `PolicyFactory.ValidateConfig`
- optional deprecated wrappers
- generated tests

DoD:

- Generated examples compile and pass.
- `testkit` contract uses factory APIs.

### Phase 5: Testkit API

Goal:

Make contract checks reusable outside `testing.TB`.

Changes:

- `CheckGeneratedRuntimePolicy`
- `MustAssertGeneratedRuntimePolicy`
- deprecated `AssertGeneratedRuntimePolicy`
- README migration

DoD:

- Contract tests cover both error and fatal helpers.

### Phase 6: Vocabulary Interface

Goal:

Allow static and dynamic vocabulary implementations.

Changes:

- `Vocabulary` interface
- `StaticVocabulary` concrete implementation
- `NewVocabulary` returns `Vocabulary`
- generated vocabulary compatibility

DoD:

- Static generated vocabulary still works.
- Dynamic test vocabulary proves interface value.

### Phase 7: Runtime Config Ergonomics

Goal:

Reduce direct struct-literal dependence without overengineering.

Changes:

- `RuntimeOption`
- `NewPolicyRuntimeConfig`
- `WithDefaultProvider`
- `WithCapabilityRoute`
- `WithProviderFallbacks`
- `WithLimits`

DoD:

- Existing struct use still works if fields remain public.
- Docs prefer options for new code.

### Phase 8: Consumer Migration

Goal:

Migrate CervoProxy and examples.

Changes:

- CervoProxy imports module `/v2`.
- Generated CervoProxy policy uses factory.
- Limit adapter handles `LimitViolations`.
- Decision handling reads `DecisionResult`.

DoD:

- CervoProxy `go test ./...` passes.
- CervoProxy build action passes.

## Merge Strategy

Recommended PR order:

1. ADR and change-management docs.
2. Error and limit contracts.
3. DecisionResult.
4. Predicate/Action contracts.
5. Generated policy factory.
6. Testkit public API.
7. Vocabulary interface.
8. Runtime config options.
9. Examples and docs migration.
10. CervoProxy migration.

Rules:

- Do not mix CervoProxy migration into core API PRs.
- Do not update generated examples without generator changes in the same PR.
- Do not rename domain primitives in the same branch as mechanical v2 migration.
- Keep package-level coverage at or above 90 percent.

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| CervoProxy breaks for longer than one PR | Medium | High | Migrate after generated policy factory stabilizes |
| Generated policy API churn | High | High | Implement factory in one focused PR with generated examples |
| Custom predicates/actions break silently | Medium | High | Compile-time interface break plus migration guide |
| v2 scope grows too large | High | High | Defer primitive renames and compile warnings |
| Runtime core gains dependencies | Low | High | Keep dependency scope test |
| Coverage drops below 90 | Medium | Medium | Coverage check after each PR |
| Consumers confuse v1/v2 packages | Medium | High | Use Go `/v2` module path and release notes |
| Structured errors overfit CervoProxy | Medium | Medium | Apply ADR 0001 cross-domain review |

## Rollback Plan

Before release:

- Revert the v2 branch or individual PRs.
- Keep v1 `main` releasable.
- Do not publish v2 tags until CervoProxy migration has passed.

After release:

- Do not overwrite v2 tags or packages.
- Publish a corrective v2 patch if package artifacts are bad.
- If migration is blocked, keep v1 packages documented as supported until v2.x
  fixes are available.

## Open Decisions

1. Should v2 use Go module path `/v2` immediately?
   - Recommendation: yes.
2. Should `Provider` be renamed?
   - Recommendation: no for v2.0; separate ADR.
3. Should `PolicyRuntimeConfig` fields become private?
   - Recommendation: no for v2.0; add options first.
4. Should generated v1 wrappers be emitted in v2?
   - Recommendation: yes for one release cycle if they delegate cleanly.
5. Should predicate/action adapter helpers be public?
   - Recommendation: yes, to reduce migration friction.
